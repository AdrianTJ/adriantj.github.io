Most Python shops end up bolting together half a dozen tools to answer one question — _what in this codebase is unused, risky, duplicated, or tangled?_ You run [vulture](https://github.com/jendrikseipp/vulture) for dead code, [ruff](https://docs.astral.sh/ruff/) for lint, [deptry](https://github.com/fpgmaas/deptry) for dependency hygiene, [tach](https://github.com/gauge-sh/tach) for boundaries, [radon](https://github.com/rubik/radon) for complexity, [jscpd](https://github.com/kucherenko/jscpd) for duplication, and [bandit](https://github.com/PyCQA/bandit) for security. Seven tools, seven configs, seven output formats, and no shared notion of what a "finding" even is.

That fragmentation is the itch [Favio](https://github.com/FavioVazquez) and I have been scratching with **[Mollify](https://github.com/FavioVazquez/mollify)** — a Rust-native engine that runs the equivalent of that whole stack in **one deterministic pass**, with one config and one output contract. This is a rundown of what it does and how to actually use it.

Mollify's one rule is the thing I care about most: **no AI invents findings.** Every result is a piece of deterministic evidence with a stable fingerprint, a confidence tier, and a human-readable reason. Mollify _produces candidates_; you — or your coding agent — decide what to do with them.

### Installing it

Mollify ships the same self-contained binary through every channel, so pick whatever fits your workflow. If you're a Python user, [uv](https://docs.astral.sh/uv/) is the path of least resistance:

```bash
uvx mollify audit              # one-off, isolated, no install
uv tool install mollify        # persistent, puts `mollify` on your PATH
```

Or the more traditional routes:

```bash
pip install mollify
cargo install mollify-cli      # from crates.io; the binary is `mollify`
```

The PyPI wheel bundles the compiled Rust binary (built with [maturin](https://www.maturin.rs/)), and the crates.io build embeds the same artifacts — so no matter how you install it, you get a byte-identical binary with the agent integrations baked in.

### The quick start

There's really only one command you need to remember to get going:

```bash
mollify audit --path /your/python/project
```

`audit` runs _everything_ and prints a 0–100 quality score on top:

```text
Mollify audit — /your/project
Quality score: 84/100
12 finding(s) across 47 file(s) — 0 error, 12 warn
  src/app.py:6   [warn/certain]  unused-export — function `_legacy` has no reachable references  (unused-export:931a82e6d41f07c3)
  src/api.py:88  [warn/likely]   high-complexity — function `handle` is complex (cyclomatic 14, cognitive 19)  (high-complexity:1aa9…)
  src/db.py:1    [warn/certain]  circular-dependency — import cycle: db → models → db  (circular-dependency:7c…)
  pyproject.toml:1 [warn/likely] unused-dependency — declared dependency `rich` is never imported  (unused-dependency:93…)
```

Every line is a piece of evidence: a rule, a location, a confidence tier, a reason, and a fingerprint. That fingerprint is content-derived and stable across file moves, which matters a lot once you start gating CI on it (more on that below).

### What it actually detects

The `audit` command is a front-end over a set of focused engines you can also run on their own. Each one maps to one of Mollify's eight categories:

| Area                      | Command              | A taste of the rules                                                                                                         |
| ------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Dead code**             | `mollify dead-code`  | `unused-file`, `unused-export`, `unused-import`, `unused-method`, `unused-enum-member`, `unreachable-code`, `commented-code` |
| **Dependency hygiene**    | `mollify deps`       | `unused-dependency`, `missing-dependency`, `transitive-dependency`, `misplaced-dev-dependency`, `unresolved-import`          |
| **Architecture**          | `mollify arch`       | `circular-dependency`, `layer-violation`, `forbidden-import`, `private-import`, custom policies                              |
| **Complexity & cohesion** | `mollify complexity` | `high-complexity`, `hotspot` (churn × complexity), `low-cohesion`                                                            |
| **Duplication**           | `mollify dupes`      | `duplication` (clone families, via suffix array)                                                                             |
| **Type health**           | `mollify types`      | `untyped-function`, `private-type-leak`                                                                                      |
| **Security**              | `mollify security`   | eval/exec, shell, SQLi, weak crypto, TLS, secrets, `try-except-pass` — each with a CWE id                                    |
| **Everything + score**    | `mollify audit`      | all of the above + the quality score                                                                                         |

A few things I find genuinely useful beyond the headline rules:

- **Jupyter notebooks** (`.ipynb`) are discovered and analyzed cell-by-cell — dead code in notebooks is a real problem nobody else catches.
- **Framework awareness.** It understands Flask/FastAPI/Django/Celery/pytest/click/Pydantic decorators, which kills the #1 false positive: your `@app.route`-decorated handler is _not_ dead code just because nothing calls it directly.
- **`mollify explain <rule>`** tells you exactly what a rule means and how it's tiered, and **`mollify trace <module>`** shows a module's import neighborhood — what it imports and what imports it.

### Being honest about uncertainty

Dead-code detection in Python is _undecidable_ in the general case — `getattr`, `eval`, and `importlib` can conjure a reference out of a string at runtime. Pretending otherwise is how static analyzers earn their reputation for crying wolf. So Mollify tiers every verdict:

| Tier        | Meaning                                                                                         | Auto-fixable |
| ----------- | ----------------------------------------------------------------------------------------------- | ------------ |
| `certain`   | Provable — a private unused symbol in reachable, non-fixture code, no dynamic dispatch in scope | ✅           |
| `likely`    | Strong static signal, small residual dynamic risk                                               | —            |
| `uncertain` | Public surface, or near `getattr`/`eval`/`importlib`                                            | —            |

Only `certain` findings are ever auto-fixed. And the quality score weights each finding's penalty by confidence, so a report full of low-confidence review items doesn't get punished like one full of proven defects. You can also filter the noise directly:

```bash
mollify audit --min-confidence likely   # drop the "for review only" candidates
mollify fix                             # preview safe removals of `certain` dead code
mollify fix --apply                     # actually write them
```

### The JSON contract

This is the part that makes Mollify programmable. Every command emits a `kind`-discriminated envelope — clients just switch on `kind` and iterate `findings[]`:

```bash
mollify audit --format json
```

```json
{
  "kind": "audit",
  "schema_version": "0.1",
  "quality_score": 84,
  "summary": { "total": 12, "errors": 0, "warnings": 12, "files_analyzed": 47 },
  "findings": [
    {
      "fingerprint": "unused-export:931a82e6d41f07c3",
      "rule": "unused-export",
      "category": "dead-code",
      "severity": "warn",
      "confidence": "certain",
      "reason": "function `_legacy` has no reachable references in the project",
      "location": { "path": "src/app.py", "line": 6, "end_line": 7 },
      "actions": [
        {
          "type": "remove-symbol",
          "description": "Delete unused function `_legacy`",
          "auto_fixable": true,
          "suppression_comment": "# mollify: ignore[unused-export]"
        }
      ]
    }
  ]
}
```

Because the output is deterministic — identical input produces byte-identical output — you can diff two reports, feed them to a script, or hand them to an agent without worrying about ordering or nondeterminism.

### Configuring it

Drop a `.mollifyrc.json` at your project root (or run `mollify init` to scaffold a documented starter). All keys are optional:

```json
{
  "severity": { "dead-code": "error", "duplication": "warn", "unused-dependency": "off" },
  "ignore": ["tests/", "migrations/"],
  "max_cyclomatic": 10,
  "max_cognitive": 15,
  "architecture": { "layers": ["api", "service", "domain", "infra"] },
  "policies": [{ "id": "no-requests-in-domain", "forbid_import": "requests", "in_paths": ["domain/"], "severity": "error" }]
}
```

Raising a rule or category to `error` is what makes CI (and agent hooks) actually _block_. The `architecture.layers` list is ordered top → bottom: a module may import its own or lower layers, but reaching _up_ a layer is a `layer-violation`. And `policies` are declarative bans — `forbid_import` / `forbid_call`, optionally scoped to paths — enforced deterministically, which is a lovely way to encode "the domain layer must stay I/O-free" as a check instead of a code-review comment.

### Wiring it into CI

Mollify was built for CI: deterministic output, real exit codes, SARIF, and a PR-scoped gate. The killer flag is `--gate new-only`, which attributes findings to changed files and only reports the ones _this PR introduced_ — so your existing tech debt doesn't block every merge:

```bash
mollify audit --gate new-only --base origin/main
# exits non-zero only if an *introduced* finding is error-severity
```

Here's a full GitHub Actions job that gates on regressions and uploads SARIF to code scanning:

```yaml
name: mollify
on: [pull_request]
permissions:
  contents: read
  security-events: write # required to upload SARIF
jobs:
  mollify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with: { fetch-depth: 0 } # needed for --gate/--base diffing
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo install mollify-cli
      - name: Audit changed code
        run: mollify audit --gate new-only --base origin/${{ github.base_ref }}
      - name: SARIF for code scanning
        if: always()
        run: mollify audit --format sarif > mollify.sarif
      - uses: github/codeql-action/upload-sarif@v4
        if: always()
        with: { sarif_file: mollify.sarif }
```

If you don't want to lean on git for diffing, there are **regression baselines** that work the same way off a content-derived snapshot:

```bash
mollify audit --save-baseline .mollify/baseline.json                    # once, on a clean main
mollify audit --baseline .mollify/baseline.json --fail-on-regression    # in CI
```

Because fingerprints are content-derived, baselines survive file moves and renames.

### The part I'm most excited about: agents and MCP

Here's the thesis. Coding agents are _constantly_ trying to reconstruct facts about your codebase — "is this function used anywhere?", "what imports this module?", "is this dependency actually needed?" — and they do it by grepping and guessing. That's slow, and worse, it's _unreliable_: an agent that greps for a symbol name misses dynamic dispatch, re-exports, and framework wiring, then confidently deletes something that was load-bearing.

Mollify flips that around. It exposes a first-class **MCP server** so the agent reads repo _truth_ — deterministic, tiered evidence — instead of reconstructing it. You start the server with one command:

```bash
mollify mcp        # stdio MCP server for coding agents
```

But you rarely run that by hand. The nicer path is the built-in scaffolder, which drops version-matched skills, rules, hooks, slash-commands, and MCP config straight into your repo:

```bash
mollify init --agent claude    # or: cursor / gemini / codex / cascade
mollify init --all             # every supported agent at once
```

For **Claude Code**, `mollify init --agent claude` writes:

- `.mcp.json` — registers the `mollify mcp` server so Claude can call it as a tool
- `.claude/skills/mollify/` — a skill that teaches the agent Mollify's JSON contract and confidence tiers
- `.claude/commands/` — slash commands for the common audits
- `.claude/settings.json` hooks — so an audit can run automatically (and _block_, if you've set rules to `error`)

The other front-ends get the equivalent, idiomatic artifacts:

| Agent               | What gets scaffolded                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------ |
| **Claude Code**     | `.mcp.json`, `.claude/skills/mollify/`, `.claude/commands/`, `.claude/settings.json` hooks |
| **Cursor**          | `.cursor/rules/mollify.mdc`, `.cursor/mcp.json`, `.cursor/commands/`                       |
| **Gemini CLI**      | `GEMINI.md`, `.gemini/settings.json`, `.gemini/commands/mollify/`                          |
| **Codex**           | `AGENTS.md`, `.codex/config.toml`, `.agents/skills/mollify/`                               |
| **Devin / Cascade** | `.devin/skills/mollify/`, `.devin/rules/mollify.md`, `.windsurf/hooks.json`, workflows     |

The whole point is that these are _committable_ — you check them into the repo, and every teammate's agent gets the same deterministic ground truth. The confidence tiers do real work here too: because only `certain` findings are auto-fixable, an agent with an auto-fix hook can safely remove provably-dead code while leaving the `likely`/`uncertain` candidates for a human to look at.

### How it's built (briefly)

Under the hood it's a Cargo workspace with a clean data flow — parse → graph → engines → report:

`mollify-parse` handles Python parsing on top of Astral's `ruff_python_parser` / `ruff_python_ast` (the same parser behind ruff), `mollify-graph` builds the module/symbol graph with real LEGB scope resolution and cycle detection, `mollify-core` holds the engines, and `mollify-cli` / `mollify-mcp` / `mollify-lsp` are the front-ends. A couple of details I think are worth calling out:

- **Real scope/binding resolution.** Reachability resolves each name _load_ to its binding, so a shadowing function-local never masks a dead top-level symbol.
- **Exact duplication.** Clone detection uses a linear-time SA-IS suffix array + LCP to find exact maximal token clones — no hash-collision guessing, and it scales to big repos.
- **Isolated engines.** If one analysis engine panics, the report still completes and carries a single `engine-panic` finding naming the culprit, instead of the whole run dying.

### Where it fits

The individual tools out there each do their one piece well. Mollify's wedge isn't "better dead-code detection than vulture" — it's the **unified deterministic pass** with a single contract, that both a human and an agent can consume:

|                                       | vulture | ruff | deptry | tach | radon | jscpd | bandit | **Mollify** |
| ------------------------------------- | :-----: | :--: | :----: | :--: | :---: | :---: | :----: | :---------: |
| Whole-project dead code               |   ✅    |  –   |   –    |  –   |   –   |   –   |   –    |     ✅      |
| Dependency hygiene                    |    –    |  –   |   ✅   |  –   |   –   |   –   |   –    |     ✅      |
| Circular deps / boundaries            |    –    |  –   |   –    |  ✅  |   –   |   –   |   –    |     ✅      |
| Complexity + churn×complexity         |    –    |  ~   |   –    |  –   |  ✅   |   –   |   –    |     ✅      |
| Duplication                           |    –    |  –   |   –    |  –   |   –   |  ✅   |   –    |     ✅      |
| Security candidates (+CWE)            |    –    |  ~   |   –    |  –   |   –   |   –   |   ✅   |     ✅      |
| One deterministic pass + MCP contract |    –    |  –   |   –    |  –   |   –   |   –   |   –    |     ✅      |

It's early but real — it's published on [PyPI](https://pypi.org/project/mollify/) and [crates.io](https://crates.io/crates/mollify-cli), has 210+ tests, and it dogfoods itself in CI. If you work on a Python codebase of any size, `uvx mollify audit` is a thirty-second way to see what it finds. And if you've got a coding agent in your workflow, `mollify init --agent <name>` is, I think, the more interesting experiment.

The code — and the docs I pulled these examples from — live at [github.com/FavioVazquez/mollify](https://github.com/FavioVazquez/mollify). Go break it and tell us what you find.
